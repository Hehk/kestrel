# Loro compatibility findings

The initial compatibility milestone is now integrated into the actual pull request page. See [current behavior, setup and remaining work](loro-integration.md). The standalone spike directory/page has been removed; interoperability tests live in `tests/review/`.

## Library and semantics

Pinned pair: Rust `loro = 1.16.0`, official `loro-crdt = 1.16.0`. Rust/npm lockfiles are committed. The application ships only the custom Rust/WASM runtime; the official package is a development-only interoperability oracle. Generated TypeScript uses `tsify::Ts`, not the deprecated ABI derives that can leak on deserialization failure.

The native and interoperability suites establish:

- Full snapshots and incremental updates in both directions, duplicate import, binary version-vector interoperability and lossless peer IDs above JavaScript's safe integer range.
- Native map ordering by Lamport, then peer ID—not wall clocks or backend arrival. Causally later writes win. This tests the proposed concurrent-device policy, not product approval for cross-device rollout.
- Same-value map inserts are skipped. Explicit reassertion uses delete/insert within one synchronous command/commit; ordinary repeated review decisions remain no-ops, including visibility.
- `LoroDoc::clone` aliases; candidate copies use `fork` and retain the current peer. Independent restores get fresh peers. The runtime serializes and persists candidates before replacing the durable document.
- Three independent replicas can preserve offline human importance, attributed agent assessments/context and explicit `inherit` across snapshot restore and reconnection. Concurrent assessment heads remain visible without an invented consensus.
- Commit grouping is not transaction isolation. Reviewed/open is a valid concurrent merged outcome.
- Missing-dependency imports discard the candidate and do not advance the durable version. A fresh VV exchange recovers missing history without retaining an unbounded pending-import queue.
- Full-history snapshots are retained; shallow snapshots and incompatible schemas are rejected. No JSON reconstruction/compaction.
- Property schedules cover commands, disconnected changes, partial dissemination, duplicate delivery and reload. Assertions concern converged views and history coverage, not serialized-byte equality.

## Untrusted network import gate

**Local persistence is implemented. Opaque network imports remain disabled.**

`export_json_updates_without_peer_compression` exposes overwritten/deleted operations, including forbidden values absent from the final view. A final-state-only validator would miss them.

However, history inspection happens after decoding. A bounded regression test demonstrates that a valid binary snapshot below the 4 MiB input cap expands into an 8 MiB payload before our validator could inspect it. This is an amplification test, not an OOM exploit or a complete library security audit. An input-byte cap is not a decoding allocation/CPU budget.

`import_trusted` and `restore_trusted` therefore accept only local data generated by this application (and trusted test fixtures). They check size, pending dependencies and schema compatibility—not complete authorization/history validity. No backend route accepts these bytes. A command's client-supplied `actor` is not authenticated provenance.

Before adding cross-device/agent synchronization:

- [ ] Choose enforceable decoder resource limits, e.g. an isolated backend worker with memory/CPU limits and bounded queues. A timeout around synchronous in-process Rust does not stop decoding work.
- [ ] Validate every newly introduced operation against server-owned scope, registered peers/provenance, permitted roots/types, immutable targets and contribution rules. Include hidden writes, divergent same-ID contributions, peer reuse and cross-user submissions.
- [ ] If bounded opaque import is impractical, explicitly revise the document/capability/transport design rather than replacing CRDT sync with implicit command replay or final-state validation.
- [ ] Approve concurrent-human/reassertion policy, recovery, retention and cross-device UX before rollout.

## Initial synthetic measurements

Single macOS arm64 run, not rollout thresholds:

| Metadata                         | Full snapshot | Restore  | One-file projection |
| -------------------------------- | ------------- | -------- | ------------------- |
| 100 assessments / 100 versions   | 6,286 bytes   | 0.125 ms | 0.131 ms            |
| 1,000 assessments / 100 versions | 67,108 bytes  | 0.159 ms | 1.463 ms            |

One thousand sequential candidate commands took 879 ms cumulatively. Snapshot import is lazy; restore timing alone is not a full load cost. The custom WASM is approximately 2.69 MB raw / 0.83 MB gzip. Reproduce metadata measurements with:

```sh
cargo run --release --locked --manifest-path crates/Cargo.toml -p review-core --example measure
```
